# UI:重複任務與日期選單

日期選單(`DueDateDialog`)、規則寫入、列表收合、移動實例的語意。伺服器端的展開與補齊規則見 `docs/tasks/data-model.md`,決策理由見 `docs/tasks/decisions.md` §6、§6a。

## 入口

**重複設定在日期選單裡,右欄沒有獨立的「重複」按鈕。** 右欄的截止日觸發鈕開日期選單;實例(`recurrenceRuleId` 不為 null)在優先級下方多一列規則摘要(`RecurrenceSummary`),它也是按鈕,點它開同一個日期選單。兩個觸發鈕由 `TaskDetail` 管理,記住是哪一個打開的,close 事件裡焦點回到它;兩者在送出後都還在,焦點不會掉到 body。新增列(`NewTaskForm` → `DueDateMenu`)的日期選單只有日期:任務還不存在,不能建規則。已完成的任務也只有日期。

## 日期選單的三列:日期、重複、結束

錨點就是選單裡的日期,不另設錨點欄位。

「重複」點開是第二層清單:不重複、每天、每週(週X)、每月(X 日)、每年(X 月 X 日)、每個工作日(週一至週五)、自訂;括號內的值由選單當下的日期推出,但目前選中、且就是既有規則那一項時用規則自己的 `startDate`(`classifyRule` 只看規則,不看截止日,從被移動過的實例打開不會變成自訂)。「自訂」是第二層的 `RecurrenceCustomFields`(頻率、間隔、星期幾),按「完成」才驗證並寫回,不停用任何按鈕。有規則時「重複」列旁有 × 代表停止重複。

「結束」只在有規則時出現:永不結束 / 按日期結束(月曆選 `until`)。規則已停止時照常可以選,選任何一項都是替這個任務建新規則。

月曆用 `expandRule` 以淡色(`--color-calendar-recurring-bg`)標示目前月份裡符合規則的日期。

第二層是同一個 `<dialog>` 裡的畫面切換:進入時焦點落在目前選中的項目(自訂是頻率的第一個選項),回主畫面時落在對應的列按鈕;Esc 在第二層只退回主畫面(攔 `cancel` 事件),在主畫面才關閉;焦點由 effect 在畫面提交後放。「清除」只清日期,並捨棄這次對重複的草稿(規則需要錨點)。草稿與送出判斷是 `src/modules/tasks/lib/recurrenceDraft.ts` 的純函式。

## 按確定時的送出

- 日期有改 → `PATCH /api/tasks/tasks/:id { dueDate }`。
- 規則:沒有規則或已停止 → `POST /api/tasks/tasks/:id/recurrence`;選不重複 → `POST …/stop`;節奏(頻率、間隔、星期幾)有改 → `PATCH /api/tasks/recurrence-rules/:ruleId`,連同 `startDate` = 選單裡的日期;只改結束日 → `PATCH { until }`,錨點不動。
- 兩者都有改時先送日期再送規則,放在 `mutate` 的**同一個佇列工作**裡:遇到第一個失敗就停(不拿被拒的日期改規則),前面已成功的仍重抓一次;焦點快照只記一次,共用重抓與遞補。都沒有改動就不送。防重複送出用 `dateSavePendingRef`,完成後一律重設。

**規則寫入會刪掉今天之後未完成的實例(含正在編輯的未來實例)並重生成新 id。** 寫入期間 `ThreeColumnLayout` 暫停「選中的任務不見就清掉 `task`」的 effect(`ruleWritePending`),結束後第一次判斷時,不見的若是剛寫入規則的那個任務,就改選這條規則最早的未完成實例(`earliestIncomplete`,與列表收合的代表同一套排序);沒有未完成實例、或改選的實例被目前檢視濾掉時才清掉。

**規則資料的重抓(`useRecurrenceRule`,規則摘要與選單的初始草稿共用)。** 規則跟著任務清單的重抓一起重抓(`ThreeColumnLayout` 的 `tasksVersion`;停止、修改規則時任務的欄位與 `recurrenceRuleId` 都不變,只看 id 會停在舊規則);同一條規則重抓時摘要沿用上一份結果,換規則才顯示載入中。日期選單則把「日期選單的寫入進行中」與「規則資料不是目前版本」都當成載入中,重複草稿等新資料到了才建立,建立時記下當時的規則,之後的判斷都用這份快照,不拿過期資料組請求;競態靠 `TaskDetail` 的 `key={task.id}` 重新掛載,effect 的 cleanup 另外標記過期,規則換了但新的還沒回來時不拿舊結果充數;載入失敗的訊息照 checklist 的方式顯示在中欄新增列下方。

## 列表收合

**重複實例在列表視圖收合成每條規則一列。** `filterTasks` 的第一步是 `collapseRecurring`,之後才套各視圖的日期條件:每條規則的未完成實例只留一個代表(`dueDate` 最早,`null` 排最後;平手比 `occurrenceDate`,再比 `id`),同組中代表以外 `dueDate < today` 的未完成實例數標在代表那一列(「+N 逾期」)。因為「錯過就跳過」會在讀取補齊時刪掉未編輯的逾期實例,「+N 逾期」自然只計入保留下來的（已編輯或上線前既有 `editedAt = 0`）實例。

先收合、後篩選,所有視圖共用同一個代表:代表是這條規則現在活著的實例,不隨視圖而變;有下限的視圖(某一天、「明天」)出現時,先篩選會在 9/17 未完成時把 9/18 選為代表(理由見 `docs/tasks/decisions.md` §6a)。已完成的實例是紀錄,不收合;一般任務原樣保留。收合只移除、不重排,順序仍是 `listTasks()` 的 ORDER BY。非代表的實例不在清單裡,也選不到。任務列 `.meta` 依序是重複圖示、「+N 逾期」、日期,都不縮。`totalCount` 仍是收合前的全部任務數,只用來分辨空狀態。

## 改實例的日期:兩種語意

**`DueDateDialog` 的第二層 `scope`。** 按確定時,任務是實例、規則仍進行中、日期有改、這次沒有同時改規則(`needsScopeQuestion`),才切到第二層,不另開對話框;日期與規則在同一次操作裡都改時不問,直接套用到整個規則。

- 「只改這一次」只送 `PATCH /api/tasks/tasks/:id { dueDate }`,`occurrence_date` 不動。
- 「改整個重複規則」送 `PATCH /api/tasks/recurrence-rules/:ruleId`,錨點改成新日期;每週時連 `weekdays` 一起送,只替換被移動的那一天(移除原定日的星期、加上新日期的星期,合併時天數減一,不會是 0)。未來的實例(`occurrence_date > today`)先移它再改規則,它會被刪掉重生,由自動改選接手;今天或逾期的實例不移動,只改規則(伺服器只從明天起重生,移動它會讓新日期出現兩筆)。

每個選項下有一行用當下日期與規則產生的說明(`src/modules/tasks/lib/recurrenceMove.ts`),改整個規則另外提醒「今天之後未完成的實例會重新產生,之前對個別實例的日期調整會消失」。不記住上次的選擇:每次進入焦點都在「只改這一次」;Esc 或「返回」退回主畫面、焦點回確定鈕,不送出。規則還沒載入完成時「改整個重複規則」顯示載入中,按了不動作(不停用)。

## 移動過的實例

`dueDate !== occurrenceDate` 時,中欄日期後面加「(原定 M.D)」(`formatListDay`,在 `.meta` 裡不縮);右欄截止日下方顯示「原定 M.D」與「還原」,按下送 `PATCH { dueDate: occurrenceDate }`,經日期選單同一條寫入佇列與防重複送出;送出前焦點先移到截止日觸發鈕(還原鈕會卸載)。列表收合的代表仍按 `dueDate` 選。

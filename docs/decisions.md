# 決策紀錄

本檔記錄已定案的決策與理由。CLAUDE.md 放「必須遵守的規則」,本檔放「為什麼這樣定」。
新決策定案後追加到對應章節;推翻舊決策時保留舊的一行,註明改成什麼、為什麼。

---

## 1. 架構

| 決策 | 理由 |
|---|---|
| 單一 Next.js app,不拆獨立 API server | 一個 process,部署最簡單;長期要搬家的需求由下一條紀律保證 |
| 業務邏輯一律寫在 `src/server/` 的純函式;route handler 只解析請求、呼叫函式、回傳 JSON | API 之後要搬到獨立伺服器,邏輯不綁框架,搬家時只換入口 |
| 驗證邏輯(如標題不可為空)放 `src/server/`;協定層解析(如網址 id 不是數字)放 route handler | 純函式是唯一入口:之後重複任務的產生邏輯或匯入 script 直接呼叫 `src/server/` 時,驗證不會被繞過。協定層解析則是 HTTP 才有的問題,搬家時會跟著入口一起換掉 |
| 驗證失敗時 throw 自訂錯誤類別(帶 `fields`),定義在 `src/server/`;route handler 用 `instanceof` 對映到狀態碼 | `src/server/` 不可以知道 HTTP 的存在 |
| 前端不從 `src/server/` import 任何東西,包括型別 | `import type` 雖不會被打包,但搬家時仍是要拆的相依 |
| 技術棧:TypeScript、Drizzle + better-sqlite3、SQLite、CSS Modules | 已定案,不提替代方案(Prisma、Tailwind、Postgres 等) |
| 各工具分開 SQLite 檔,表名保留前綴 | 工具之間資料獨立,首頁摘要另行處理 |
| 登入暫不做,身分檢查獨立成中介層 | 只在 Tailscale 網內使用 |

## 2. 資料模型

| 決策 | 理由 |
|---|---|
| 日曆日期存 `YYYY-MM-DD` 文字;絕對時刻存 Unix 整數秒 | 截止日是「哪一天」,不是時刻,存成時刻會有時區偏移問題 |
| 完成狀態用 `completedAt` 時間戳,不用布林值。寫入時對外收 `done: boolean`,時間由 `src/server/` 寫入,且冪等:未完成收到完成 → 寫當下時間;已完成收到完成 → 保留原值;收到未完成 → `null`(已是 `null` 不變)。適用於所有有完成狀態的實體(任務、checklist 項目,以及之後的新實體) | 同時記錄「有沒有完成」與「何時完成」,之後回顧需要;冪等讓重複送出(重試、連點)不會改寫原本的完成時間,「何時完成」才可靠 |
| `task` 表保留 `parentTaskId` | 預留子任務 |
| `priority` 值域 0 / 1 / 3 / 5(無/低/中/高),越大越重要 | 留間隔供之後插入新等級;`null` 在 `src/server/` 正規化成 0 |
| 目前硬刪除 | MVP 測試階段沒有真實資料;加軟刪除前刪掉的資料不可復原,這點已知並接受 |
| 預設排序:未完成在前、已完成在後,組內依 `createdAt` 升冪;排序在 SQL 層做 | 參考 TickTick;SQL 排序為之後的分頁鋪路 |

## 3. API

| 決策 | 理由 |
|---|---|
| REST 風格,錯誤碼三種:`VALIDATION_FAILED`(400)、`NOT_FOUND`(404)、`INTERNAL_ERROR`(500) | 所有工具共用同一套錯誤形狀 |

## 4. 前端資料流

| 決策 | 理由 |
|---|---|
| 所有資料由 Client Component 經 HTTP fetch 取得;不用 Server Component 直接 import,不用 Server Action | 只有一條資料路徑,好除錯;API 搬家時只換網址 |
| 任何寫入後重抓整份清單、整份替換 state;不做樂觀更新。例外:checklist 拖曳與習慣計數(理由各見 §5、§6b) | 資料庫是唯一事實來源,畫面是它的投影;之後加排序或篩選時,前端不必重算一次後端的邏輯 |
| 唯一例外:標題與描述在聚焦期間由該輸入框自己的 local state 持有,失焦後才跟隨伺服器資料 | 慢網路下重抓回來的舊值會蓋掉使用者正在打的字 |
| 擋住操作的狀態(disabled、readOnly)的外觀一律延遲 `--disabled-delay`(250ms)才顯示。目前適用:ConfirmDialog 的確認鈕 | 阻擋與呈現分開:阻擋照常立即生效,但本機請求在延遲內完成時畫面完全不變化,只有慢速請求才顯示停用樣式 |
| 任務陣列與 fetch 放在 `ThreeColumnLayout`,中欄與右欄都從這份讀 | 右欄從清單挑資料,不另開 `GET /api/tasks/[id]` |
| 選取狀態只存在網址(`?view=…&task=…`);`useSearchParams` 在 `ThreeColumnLayout` 讀一次往下傳 | 網址是唯一來源;重整、分享、上一頁都一致 |
| `task` 參數找不到對應任務時,在 `useEffect` 裡把它從網址移除,右欄回空狀態 | 副作用不能寫在渲染過程;例如改了截止日後任務離開目前檢視 |
| 上一條的例外:規則寫入(修改、停止)後選中的實例消失時,改選這條規則最早的未完成實例;沒有任何未完成實例才回空狀態 | 修改規則會刪掉今天之後未完成的實例並重生成新 id,只要代表的日期在今天之後,正在編輯的那個實例一定會消失;這是常見情況,不是邊緣案例。伺服器邊界不變:代表也要重新產生,否則把每週一改成每週四,代表還停在週一 |
| 用到 `useSearchParams` 的元件必須被 `<Suspense>` 包住 | 否則 `npm run build` 失敗 |
| `TaskDetail` 以 `key={task.id}` 掛載;切換任務時右欄的所有狀態(欄位草稿、錯誤訊息、確認彈窗)隨卸載清除 | 狀態生命週期綁在掛載上,不必逐一手動清除 |

## 5. 編輯行為

| 決策 | 理由 |
|---|---|
| 標題、描述、checklist 直接改直接存;優先級點選即存;日期選好按確定才存 | 各欄位分開儲存,依操作性質決定時機 |
| 描述與 checklist 分開 | 兩者資料形狀不同 |
| 刪除鈕在右欄,不在任務列 | 刪除是對已選取任務的操作 |
| 刪除確認用原生 `<dialog>` + `showModal()`;按鈕順序取消在前,預設焦點在取消 | Enter 的預設結果要安全 |
| 確認彈窗的開啟狀態存任務 id,不存布林值 | 布林值在刪除成功後會殘留到下一筆任務 |
| 刪除後不自動選取下一筆，右欄回空狀態 | 選取是使用者的明確動作，不由系統代做 |
| 刪除後鍵盤焦點落到被刪任務在畫面順序中的下一筆;刪的是最後一筆時落前一筆;清單空了才落中欄清單容器(`tabIndex={-1}`) | 鍵盤使用者從原位置繼續，不必從頭 Tab(6b-3 補充，取代「一律落容器」) |
| 日期彈窗:沒有截止日時草稿預設為今天，月曆上今天顯示為選中;按「確定」才存 | 常見預設，且未按確定不會寫入，預選不會造成誤存 |
| 日期彈窗開啟時焦點落在彈窗本身 | 有無截止日兩種情況焦點起點一致;焦點不落在任何按鈕上，避免 Enter 直接觸發動作 |
| 欄位被伺服器拒絕時保留輸入值、欄位標示錯誤、訊息顯示在欄位下方、再次輸入即清除訊息 | 使用者修正輸入，而不是重打;取代早期的「還原舊值」 |
| 任務列的勾選框自繪(input type=checkbox 加 appearance: none) | 原生勾選框無法依優先級改未勾選時的框線顏色 |
| 已完成任務的勾選框用單一 ink-soft,不保留優先級顏色 | 已完成是一個群組,群組內再分層級等於對不需要行動的事施加視覺層級;實心色塊比空心框重,保留會讓已完成比未完成搶眼 |
| 右欄與新增列共用同一組觸發鈕與選單(PriorityMenu、DueDateMenu);右欄的觸發鈕顯示「圖示 + 目前的值」,新增列只顯示圖示 | 新增列是設定,空值是預設;右欄要讀得出目前狀態 |
| 截止日維持 DueDateDialog(選好按確定才存),只統一觸發鈕外觀 | 要統一的是視覺語彙,不是互動模型 |
| checklist 只有一個新增入口（底部新增列），不支援在項目內按 Enter 插入；順序用拖曳調整 | 兩個新增入口的行為不同；草稿機制的邊界情況（焦點交接、錨點失效）成本高於「插到中間要多拖一次」 |
| checklist 拖曳排序採樂觀更新(全 app 兩個樂觀更新之一,另一個是習慣計數,見 §6b)；寫入排隊中不能開始拖曳 | 等回應的話，放手時項目會先彈回原位；排隊中拖曳，先完成的寫入會用重新 fetch 蓋掉拖好的順序，後送的 PUT 也會因陣列不吻合被拒 |
| 任務與 checklist 的寫入都經過佇列，控制項在寫入期間不停用 | 有焦點的元素被停用時瀏覽器會把焦點移到 body；停用也會吞掉寫入期間的點擊 |
| 任務從目前視圖消失（刪除、勾選完成、改欄位離開篩選）時，焦點移到遞補列；原本在勾選框就移到遞補列的勾選框 | 從視圖的角度，離開與刪除結果相同，共用一套規則；勾選框對勾選框讓鍵盤可以連續勾選 |
| 對話框一律經 dialog.close() 關閉（確定、清除、取消、Esc、背景點擊同一條路徑），在 close 事件中明確把焦點移回觸發鈕；會卸載觸發鈕的動作（如確認刪除）除外 | 直接卸載開啟中的 <dialog> 時，瀏覽器不會歸還焦點；自動歸還的行為各瀏覽器不一致（Safari 點擊按鈕不會給它焦點） |

## 6. 重複任務(已定案,未實作)

| 決策 | 理由 |
|---|---|
| 「任務」(日曆規則,如每月繳費)與「習慣」(配額,如每週健身兩次)是兩個獨立實體 | 資料模型本質不同 |
| 實例事先產生(讀取時補齊);改實例只改該實例;改規則保留已完成、重生未完成 | 已完成的紀錄不被規則變更改寫 |
| 結束用「停止重複」按鈕,不設預設結束日 | |
| 不做跨週期目標連動 | 複雜度與需求不成比例 |

## 6a. 重複任務(R1 資料層)

| 決策 | 理由 |
|---|---|
| 規則是日曆規則(freq / interval / weekdays / startDate),不是「完成後 N 天」 | 繳費、會議這類重複依日曆發生,不隨完成時間漂移 |
| 展開只依日曆計算:只看 startDate 與規則參數,不看上一次實例或完成時間;monthly 每個月從 startDate 的日重算,沒有那天取月底 | 結果可重現,虛擬展開與實體實例永遠一致;從上一次推算會讓 1/31 變成一路 28 號 |
| 錯過的日期保留為逾期,且全部補出,不設回溯上限 | 錯過是事實,悄悄略過等於替使用者決定「那次不用做」 |
| 建立規則時不回溯:規則建立前的日期不產生實例;原任務是第一個實例(截止日不變,逾期就維持逾期),之後從今天開始補 | 「錯過全部補出」只適用於規則存在期間;規則建立前的日期沒有被錯過。否則兩個月前的任務設成每天會一次補出約 60 個逾期實例 |
| 實體實例只產生到補齊終點(今天 + 6,對上「未來 7 天」);之後的日期由 `expandRule` 虛擬展開 | 實例要能勾選、編輯,必須是資料列;更遠的日期只需要被看見,不需要落地 |
| 規則以水位線 `generatedThrough` 記錄已產生到哪一天;補齊只往前,產生過的日期不再產生 | 使用者刪掉的實例不會在下次讀取時復活;唯一鍵 `(recurrenceRuleId, occurrenceDate)` 另外擋重複 |
| 改規則與停止重複共用同一個邊界:只刪除今天之後、未完成的實例;今天的、逾期的、已完成的不動 | 已經發生或正在發生的紀錄不被規則變更改寫 |
| 改規則、停止前,先用舊規則補到最新 | 之後 API 可以不經過 `listTasks` 直接呼叫;水位線落後的那段是舊規則下的逾期與今天實例,照「錯過全部補出」必須存在 |
| `GET /api/tasks` 會補齊實例:不是 safe,但是冪等(水位線 + 唯一鍵,重複呼叫不會多產生實例) | 「讀取時補齊」的直接結果 |
| 所有列表視圖每條規則只顯示最早的未完成實例,並標示逾期數;收合在日期篩選之前,且所有視圖共用同一個代表 | 代表是「這條規則現在活著的實例」,不應隨視圖而變。現有四個視圖的日期條件只有上限,兩種順序結果相同,所以這條目前驗不出來;有下限的視圖(日曆的某一天、「明天」)一出現就看得到差別:9/17 未完成時,先收合則 9/18 那天不顯示這條規則,先篩選則會把 9/18 選為代表。已完成的實例是紀錄,不收合。「哪幾天被佔用」交給之後的日曆視圖,列表視圖回答的是「接下來要做什麼」 |
| `until` 含當天 | 「做到 9/30」的直覺是 9/30 那次也要做 |
| `until` 與 `ended_at` 分開:`until` 是規則的一部分,`ended_at` 是使用者中途停止;到期不自動寫 `ended_at` | 自動寫入的話分不出「規則本來就到這天」和「使用者提前停止」 |
| `firstOccurrence` 不看 `until` | 它的語意是「錨點之後第一個符合規則的日期」,是純曆法問題;`createRuleFromTask` 需要它來和 `until` 比較,讓 `until` 影響它會形成循環 |
| `until` 允許早於今天 | 這樣的規則等同已到期,不產生新實例;加「不得早於今天」的限制會讓修改歷史規則變得困難 |
| 已停止的規則摘要不寫「直到」 | 停止是既成事實,`until` 是不會發生的計畫;兩段並列會矛盾 |
| 停止重複可逆:任務的規則已停止時可以建新規則,任務改指向新規則;舊規則與其實例保留為紀錄 | 「不設預設結束日,用按鈕停止」沒有說不可逆;不可逆的話,停止之後這個任務再也無法設定重複,只能刪掉重建 |
| 重複設定併入日期選單,錨點就是選單裡的日期,不另設錨點欄位 | 多一個日期欄位就多一種「錨點和日期不一致」的狀態要解釋 |
| 改實例的日期時詢問「只改這一次/改整個規則」,不記住上次的選擇 | 兩種意圖都常用,從外面看不出是哪一種;記住上次會讓下一次默默做錯 |
| 日期與規則在同一次操作裡都改時不詢問,直接套用到整個規則 | 既然改了規則,操作對象本來就是整條規則 |
| 改整個規則時,每週只替換被移動的那一天(移除原定日的星期、加上新日期的星期) | 動的是這一個時段,其他天沒有被碰到;每週一、四把週四移到週五是一、五,週一那次不該跟著變成週二 |
| 今天或逾期的實例選「改整個規則」時,這個實例不移動,只改規則 | 伺服器只重生今天之後的實例;移動它的話,新規則從明天起又產生同一天的實例,新日期會出現兩筆 |

## 6b. 習慣(H1 資料層與 API)

| 決策 | 理由 |
|---|---|
| 習慣與重複任務是兩個獨立實體,習慣是配額、任務是日曆規則 | 重複任務回答「哪天要做」,習慣回答「這個週期做了幾次」;資料形狀與判定方式都不同(§6 第一條的落實) |
| 完成次數存成 log(每次一列),不存週期累計數 | 回顧要能看到哪天做的 |
| 週期與目標的變更寫 `habit_settings_history`,每次追加完整的一筆(`periodType` + `target`);`habit` 上的是現在設定的快取;歷史週期用當時的設定判定 | 不用現在的目標回頭重算,否則降低目標會讓斷掉的 streak 自己接回來。週期與目標記在同一張表:兩者都是「某個設定從哪天起生效」,分兩處存要同時維護,漏一邊就不一致 |
| 改週期時 streak 從變更日所屬的週期重算,舊週期的紀錄不參與;只改目標不重算 | target 的單位跟著週期:每天 1 次改成每週 1 次後,用新週期重新解讀舊紀錄,幾乎每週都「達成」 |
| 每個週期用它最後一天(不超過今天)生效的 target 判定 | 當前週期因此等於現在的設定,與進度顯示一致;改目標當週立即生效。過去的週期用它結束時的目標,之後的修改不回頭改寫 |
| 某個週期當時的 target 為 null(紀錄型)時 streak 停在那裡。後果:紀錄型改成有目標之後,streak 從那天起算,先前的紀錄不參與 | 紀錄型沒有「達成」可言,不能拿之後的目標回頭判定。這和「改目標不重算」不衝突:那一條指的是有目標 → 有目標,歷史照當時的目標判定;這一條是當時根本沒有目標 |
| 停止不建新實體,用 `habit_pause` 記區間;停止期間的週期跳過,不計入也不中斷 | 停止是習慣的一段狀態,不是另一個習慣;跳過而不中斷,旅行、生病回來 streak 還在 |
| 週期與停止區間有交集就跳過,不要求完全覆蓋;`endDate` 含當天 | 週中開始停止的那一週本來就做不滿;恢復當天也算停止過,照同一條規則處理,不另開例外 |
| 停止中不能新增 log;未來日期不能記;過去日期可以補登 | 進度依日期分組計數,未來的 log 會算進當前週期的進度;停止中記錄與「停止」矛盾 |
| streak 單位跟著週期;當前週期未達成不算斷 | 週期還沒結束,未達成是「還沒」不是「沒做到」 |
| 刪除習慣是硬刪除(同 task),log、設定歷史、停止區間一起刪。要保留紀錄請用停止 | 與 §2「目前硬刪除」一致;刪除會一併失去所有 log,停止才是保留紀錄的做法 |
| 停止、恢復重複呼叫時拒絕(400),不冪等 | 和「停止重複規則」不同:習慣的停止會寫一段新區間,重複呼叫多半代表畫面過期,拒絕比默默接受更容易發現 |

### H2:習慣的 UI

| 決策 | 理由 |
|---|---|
| 計數用 PUT 絕對值(`PUT /api/habits/:id/logs?date=` `{ count }`),不用 +1 相對操作 | 連按時相對操作的失敗不會自我修正;絕對值是最後一筆決定結果,中途的請求順序不影響最終狀態 |
| 習慣計數採樂觀更新(全 app 第二個例外):每個習慣一份覆寫值,顯示與送出的 count 來自同一個覆寫值;這個習慣排隊中的 PUT 全部送完、重抓回來後才清掉。失敗時清掉覆寫值並重抓,中欄錯誤區明講「次數已還原」 | 圈圈是連續操作(連按數下),等每一次往返才更新畫面會讓下一下按在尚未更新的畫面上;其他寫入都是單次操作,不適用。拿伺服器回來的舊值算 count 的話,連按時顯示與送出會分岔 |
| +1 一律記在今天;-1 作用在本週期最近有紀錄的那天(`periodCounts` 的第一筆),那天歸零後下一次退回作用在再前一天 | 只退今天的話,週一記過、週三想取消時已勾的圈圈點不動,可點與否無法從畫面判斷。週期跨過之後舊週期不在 `periodCounts` 裡,退回動不到 |
| 圈圈只能由左至右點,可點的是第 count+1 顆(+1)與第 count 顆(-1);每次只動一筆 | 位置和次數一一對應,點哪顆就知道結果;跳著點會讓一次點擊寫入或刪除好幾筆 |
| 滿額收合成大勾加一顆小圈圈;有超額時大勾不可點(`aria-disabled`,沒有 pointer),要從右邊的超額圈圈或 +N 一顆一顆退 | 同上一條:可點的只有最後一顆;超額時點大勾一次刪掉好幾筆會違反它 |
| 圈圈的深淺編碼已勾與未勾,不是位置 | 固定深淺會讓勾選後畫面沒有變化 |
| 圈圈上限 target <= 6,超過改數字加 −/+ | 圈圈太多時數不出來,也塞不進一列 |
| 中欄小區塊出現在今天與未完成兩個視圖,可收合,狀態存 localStorage(在 effect 裡讀) | 這兩個視圖回答「接下來要做什麼」,習慣屬於同一個問題。伺服器端沒有 localStorage,render 時讀會 hydration 不一致 |
| 中欄小區塊只列本週期未滿額、進行中、有目標的習慣;紀錄型不列,也不算進「習慣 N/M」 | 規則是未滿額才顯示、滿額離場;紀錄型永遠不滿額,會固定掛著,區塊「自己變空」的訊號就消失,摘要也永遠走不到 N/N |
| 中欄小區塊只要有進行中、有目標的習慣就出現;全部滿額時保留標題列並顯示「本週期的習慣都完成了」 | 全部滿額是今天的成果,區塊直接消失會像壞掉 |

## 6d. 清單呈現:分組、排序、置頂

| 決策 | 理由 |
|---|---|
| 分組(group by)與排序(sort by)是兩層正交設定:分組把清單切成有標題的區塊,排序決定每個區塊內部的先後 | 參考 TickTick。兩者混成一個設定的話,「依優先級分組再依日期排序」這種常見組合表達不出來;選「無分組」時自然退化成只有一層排序 |
| 只做依條件自動排序,**不做**手動拖曳排序 | 使用者明確選擇。連帶否決:`task` 不加排名欄位,fractional indexing(排名值取前後兩者中間值,一次拖曳只寫一筆)整套不需要。之後若要加手動排序,再評估整數 position 與 fractional indexing |
| 排序方式與分組方式是**視圖設定**,存在獨立的設定表,每個清單各存一份(`group_by` / `sort_by` / `sort_direction`) | 它描述的是「現在想怎麼看這個清單」,不是任務的屬性;每個清單各自記住是 TickTick 的行為,也符合「收集箱要看日期、Study 要看優先級」的實際用法 |
| `ORDER BY` 最後一層固定用 `created_at`(再以 `id` 打破平手)當決勝鍵 | 依優先級排時同優先級的任務,資料庫不保證回傳順序穩定,重新整理後順序會跳動;決勝鍵讓順序是決定性的。與 §2「預設排序」的既有做法一致 |
| 空值沉底:沒有日期的任務在依日期排序時排最後,沒有優先級的在依優先級時排最後 | 「未設定」不是一個等級,放在有值的任務之間會被誤讀成介於兩者之間 |
| 分組鍵不一定是欄位值:依清單、依優先級直接取欄位;依日期是動態計算的桶(逾期 / 今天 / 明天 / 本週 / 更晚 / 無日期) | 日期的桶是相對今天的,不能存成欄位;與 `views.ts` 的日期篩選是同一類計算,共用同一份「今天」 |
| 系統區塊凌駕使用者的分組設定:習慣固定自成一區,不受 `group_by` 影響 | 習慣在資料模型裡是獨立實體(§6b),本來就不走任務的分組與排序規則 |
| 置頂是 `task` 上的布林欄位 `pinned`,語意是**全域**的:在收集箱置頂,在「今天」這類智慧清單也置頂 | 若要讓置頂只在某個清單生效,就不是布林欄位而是 `(task_id, list_id)` 的關聯,成本高出許多,且「這件事現在最重要」本來就與從哪個清單看無關 |
| 置頂採「跨分組的獨立區塊」(A 案):置頂任務從原本的分組抽離,固定在最上方;分組標題旁的計數在抽離後才算 | TickTick 的做法,置頂的東西一眼看得到。代價是計數要扣除,否則「高優先級 1」與畫面上的筆數對不上。被否決的 B 案(置頂只在各自分組內排最前)沒有計數問題,但置頂任務會散落在各區塊,失去置頂的意義 |
| 置頂區塊內部不做手動排序,沿用當前的 `sort_by` 加決勝鍵 | 與「不做手動拖曳排序」一致 |
| `pinned` 與清單視圖設定表在這一輪一起進 schema | 之後補欄位要寫 migration 並回填既有資料 |

實作時定案:

| 決策 | 理由 |
|---|---|
| 分組、排序、置頂在前端算(`src/lib/listView.ts` 的 `arrangeTasks`),不走 SQL `ORDER BY`、不加 `?sort=`。取代本節「`ORDER BY` 最後一層」的字面做法:決勝鍵的規則不變,改由比較函式實作 | 篩選本來就在前端(`filterTasks`),`GET /api/tasks` 一次拿全部、各清單共用同一份;分組的日期桶又是相對今天算的,只能在篩選之後做。排序若放伺服器,換清單與每次寫入後的重抓都要帶排序參數,換清單時還會先看到舊順序。純函式放 `src/lib/`,伺服器之後要分頁時可以直接呼叫同一份 |
| 設定表 `task_list_view` 以 `listKey`(文字)為主鍵,目前的值是智慧檢視的 id | 智慧檢視沒有資料列可以掛外鍵;自訂清單出現時用另一種前綴,不必改表 |
| 預設值不落地:沒有列就用 `defaultSettings`。今天與未來 7 天預設依日期分組,其餘不分組 | 之後改預設時,沒動過設定的清單跟著變。今天與未來 7 天混著逾期與未到期的,預設就該分得開(併掉 backlog 的「逾期 / 今天 / 之後的區段標題」) |
| 排序欄位:建立時間、截止日、優先級、標題;方向可切換,換欄位時回到該欄位的起始方向(日期近的在前、優先級高的在前) | 從「標題 Z → A」換到優先級時沿用降冪剛好對,從「截止日近的在前」換過去沿用升冪就會變成低的在前;方向的意義跟著欄位,不能直接沿用 |
| 分組的桶順序固定,不跟排序方向走 | 方向是區塊內的事;逾期永遠在今天上面 |
| 設定的寫入不做樂觀更新,PUT 後重抓 `GET /api/list-views` | 與 §4 一致;樂觀更新的例外仍然只有三個 |
| 已完成的任務不進置頂區塊 | 置頂的意義是「現在最重要」;已完成視圖裡再分一塊置頂沒有資訊量 |
| 置頂的切換放在右欄,不放任務列 | 與刪除同理:是對已選取任務的操作;任務列右側留給日期 |
| 區塊標題不可收合 | 這一輪先不做;要做時收合狀態存哪裡(localStorage 或設定表)要另外決定 |

待決:

- 重複任務的置頂不跟著規則:置頂的是某一個實例,它完成後下一個實例不是置頂。要跟著規則就得在 `task_recurrence_rule` 加 `pinned` 並在產生實例時複製

- 依標籤分組時,一個任務有多個標籤會在多個區塊各出現一次。接受重複呈現,或改成只取第一個標籤。(標籤本身排在最後做,這條可以跟著延後)

## 6e. 目標(規劃中,尚未實作)

| 決策 | 理由 |
|---|---|
| 目標是獨立的實體,不是任務,也不是「一種清單」 | 任務是可完成的離散動作,有到期日、完成即消失;目標是方向或狀態,不被排程,在意的是進度不是完成。清單是純收納,沒有結束狀態、沒有時間軸、不需要進度——目標這三項都有,所以不能用「清單加一個 flag」代替 |
| 現在就建 `goal` 表,即使第一階段只做新增 / 列出 / 編輯 / 改狀態 | 用清單代替的話,之後拆開不只要搬資料,還要回頭改所有讀 `list` 的查詢與左欄 UI(它們都預設「清單 = 可放任務的收納容器」);現在多一張只有基本欄位的表,成本接近零 |
| 分類用 `goal_type`(`project` / `milestone` / `metric` / `pursuit`),**不用**短 / 中 / 長期 | 時間長度只是表象,真正影響資料模型的是完成條件的型別:`project` 有終點且可分解成任務(完成實習研究);`milestone` 有終點但不可分解,是二元狀態(養一隻狗);`metric` 的進度是一個數字且來源在系統外(存到多少錢、肌肉量);`pursuit` 沒有終點,只問最近有沒有在推進(學荷蘭文)。長度可以從 `target_date` 反推,型別沒辦法 |
| 不做目標的層級巢狀(`parent_goal_id`) | 一有層級就要定義「子目標完成度如何匯總成父目標進度」,而二十年尺度的目標沒有可靠的完成度定義 |
| 第一階段欄位:`id` / `title` / `description` / `goal_type` / `status` / `target_date`(可空) / `created_at` | 全部延後項都是「加欄位」,舊資料維持 NULL,不需回填 |
| 任務與目標的關聯延後,形式是 `task.goal_id`(可空外鍵);同時預期需要 `habit.goal_id` | 任務關聯只對 `project` 型有意義;`pursuit` 型(學荷蘭文)連動的對象其實是習慣(每天讀 30 分鐘)。進度來源依型別而異:`project` 看任務完成比例,`pursuit` 看習慣的達成紀錄 |
| 任務同時屬於一個清單和一個目標,兩個獨立的軸 | 清單回答「這件事收在哪」,目標回答「這件事為了什麼」。把目標做成「另一種清單」會逼使用者決定任務歸哪一邊 |
| `metric` 型延後到 PACR 併入後才接資料來源(`current_value` / `target_value` / `unit` + 來源設定) | 存款金額的真實來源是記帳工具,肌肉量是體外測量。來源接上之前只能手動更新,手動更新的數字很快就過期,而且不會有人去維護它。第一階段 `metric` 型只有標題與描述 |

待決:

- 「人生的 50 個目標」現在先當普通清單用(裡面的項目沒有到期日,不會跑進「今天 / 未來 7 天」,不干擾日常),等目標功能做好再搬過去;或一開始就建進 `goal` 表。後者省掉之後的搬遷

## 6f. 批次貼上新增

| 決策 | 理由 |
|---|---|
| 綁在 `paste` 事件上,不是每次輸入都判斷;從剪貼簿取 `text/plain` | 從 Notion、網頁複製會同時帶 HTML,取純文字才不會夾帶格式 |

| 決策 | 理由 |

| 超過 100 行時不跳確認框,照一般貼上處理 | 上限的目的是擋誤貼;跳一個只能取消的框沒有比直接貼入多給什麼 |
| 確認框沿用 `ConfirmDialog`,確認鈕用行動色(`tone="action"`),取消鈕的字是「貼成一行」;預設焦點仍在取消 | 不是破壞性動作,不該是紅色;取消在這裡有具體結果,按鈕要寫出來。Enter 的預設結果維持安全的那一邊(§5) |
| 中欄批次建立的每一筆套用新增列草稿的日期與優先級 | 草稿是「接下來要建立的任務」的設定,一次建多筆也適用 |
| 批次端點是獨立的路徑(`/api/tasks/batch`、`…/checklist-items/batch`),不讓原本的 POST 同時收物件與陣列 | 一個端點一種 body 形狀,錯誤的 `fields` 形狀也才固定 |
| 只有標記、沒有內容的行(單獨一個 `-`)丟掉;`-5 度`、`3.14` 這種標記後面沒有空白的不剝 | 標記的定義是「符號加空白」;否則會吃掉負數與小數 |

## 7. 樣式

| 決策 | 理由 |
|---|---|
| CSS 變數分兩層:色票層 `--palette-*`(名字只描述顏色)與語意層 `--color-*`(名字描述用途);元件只引用語意層 | 調色只動色票層,元件不必改(本條取代 Session 3 的「單層語意」) |
| 元件 `.module.css` 不寫死顏色、間距、字級、字重、字型 | 之後抽共用設計系統時不必逐檔翻找 |
| 字型用系統字型堆疊,不載入字型檔;中文 fallback 指定蘋方/微軟正黑體 | 目前主要在 MacBook 上用;跨裝置一致等做共用設計系統時再決定 |
| 字級、字重已 token 化,字級以 rem 表示 | 改字級只動 `:root` |
| 鍵盤焦點:全域 :focus-visible 用 ink-soft 外框,偏移 2px | 全頁單一顏色;偏移讓外框畫在頁面底色上,因此不受按鈕底色影響(ink 在 accent 上只有 2.82) |
| hover 與選取分開;選取 = 底色 + 左側色條;層級應為選取 > hover | 目前 hover 比選取顯眼是色票值問題,留待色票第二輪 |
| 左欄與中欄文字單行截斷(`…`),右欄換行;日期與優先級標記不縮 | 空間不足時只犧牲標題 |
| 深色模式暫不做 | 語意層命名保證之後只需加一組覆寫 |
| 任務列的優先級只用顏色(勾選框框線加淡色填底),不用文字;文字標籤只在右欄與新增列 | 任務列右側已有日期,再加標記會壓縮長標題的寬度 |
| 優先級色作為標記而非文字,門檻是 3:1 而非 4.5:1 | 舊值當文字色調而被壓暗,三者亮度幾乎相同(低 vs 高 對比 1.00),只剩色相差,在 16px 上分不出來 |
